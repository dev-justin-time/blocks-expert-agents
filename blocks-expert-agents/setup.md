# Blocks Deployment Plan

This plan deploys the three independent TypeScript agents in this repository:

- `spane-expert` — SPANE psychology knowledge base
- `blocks-streaming-expert` — Blocks and agent-streaming knowledge base
- `integrated-knowledge-agent` — in-process router combining the two knowledge domains

The agents run on infrastructure that you control. Blocks provides the network connection, task routing, presence, and catalog; it does not host the handler process for you.

## 1. Current repository model

Each agent is a standalone Blocks provider project with:

- `agent-card.json` — public metadata, input/output contract, and runtime settings
- `handler.ts` — default-exported TypeScript handler
- `trigger.ts` — network smoke-test client
- `package.json` — SDK and CLI scripts
- `data/` — CSV knowledge base files

The repository has no root `package.json` or deployment orchestrator. Deploy and operate each directory separately. The integrated agent currently performs its routing in-process; it does **not** call the other two agents through `ctx.taskClient`, so there is no Blocks registration-order dependency between them.

## 2. Prerequisites

Install or provision:

- Node.js 22 or newer
- npm
- A Blocks account with permission to register agents
- The Blocks CLI:

```bash
npm install -g @blocks-network/cli
# Alternative installer:
# curl -fsSL https://config.blocks.ai/install.sh | sh
```

For a VM or restricted corporate network, allow outbound HTTPS on port 443 to:

- `config.blocks.ai`
- `api.blocks.ai`
- `*.pndsn.com`

No inbound port, DNS record, static IP, or port forwarding is required. If an HTTP proxy performs TLS inspection, make sure Node trusts the proxy CA.

## 3. Prepare the existing projects

Blocks' Node.js SDK is hosted through the registry configuration generated by `blocks init`. The checked-in agent directories currently contain `package.json` files but do not contain the generated `.npmrc`, `.env`, or `.gitignore` files. Before installing dependencies:

1. In a temporary directory, run the documented Node provider scaffold:

   ```bash
   mkdir blocks-scaffold
   cd blocks-scaffold
   blocks init bootstrap_agent --mode provider --language node -y
   ```

2. Copy **only** the generated `.npmrc` registry configuration into each existing agent directory. Do not overwrite the existing `package.json`, handler, card, or data files, and do not copy credentials into source control. Remove the temporary scaffold when finished.
3. Before logging in, create or verify a `.gitignore` in each agent directory containing at least:

   ```gitignore
   node_modules/
   .env
   ```

   For a new file, from each agent directory you can run:

   ```bash
   printf 'node_modules/\\n.env\\n' > .gitignore
   ```

   Verify with `git check-ignore .env node_modules` before proceeding. The current repository does not include these generated ignore files.
4. Do not manually create `BLOCKS_API_KEY`. Blocks writes it during login.
5. From each agent directory, install dependencies:

   ```bash
   npm install
   ```

If `npm install` returns a 404 for `@blocks-network/sdk`, stop and fix the `.npmrc` setup before continuing.

## 4. Validate and register each agent

Run the following from the repository root. Each `npm run check` invokes `blocks check`, which validates the agent card, handler path/export, names, and schema.

```bash
cd spane-expert
blocks login --write-env
npm install
npm run check
npm run register
cd ..

cd blocks-streaming-expert
blocks login --write-env
npm install
npm run check
npm run register
cd ..

cd integrated-knowledge-agent
blocks login --write-env
npm install
npm run check
npm run register
cd ..
```

`blocks register` creates a private, free agent by default. This is the recommended staging state. Registration does not run the handler; the process still needs to be started in the next step.

Before proceeding, verify that each agent has:

- A valid, unique `identity.agentName` using only letters, numbers, and underscores
- A meaningful display name and description
- An input id of `request`, matching the `textPart(..., 'request')` calls in the triggers
- An output id of `result`
- A handler path of `./handler.ts` and `handlerExport` set to `default`
- Its required CSV files present under `data/`

### Input contract check

The cards declare `application/json` inputs with a JSON schema, while the existing triggers pass `JSON.stringify(...)` through the SDK's `textPart` helper. Confirm this combination with `blocks check` and an actual private trigger before publishing. If Blocks rejects the request, resolve the mismatch before publishing by using the structured JSON/Form part helper exposed by the installed SDK (inspect its TypeScript exports), or by changing all three cards to `text/plain` and keeping the current stringified payload/handler behavior. Do not mix the two contracts, and do not publish until the card, handler, and trigger agree.

## 5. Start the agents

`blocks run` is a long-running process. Start one process per agent in three terminals, or use a process manager on a VM.

### Separate terminals

```bash
cd spane-expert && npm run run
cd blocks-streaming-expert && npm run run
cd integrated-knowledge-agent && npm run run
```

Keep all three processes running. If a process exits with `BLOCKS_API_KEY is required`, rerun `blocks login --write-env` from that agent's directory. If it hangs or cannot connect, check outbound HTTPS access and proxy settings.

### VM process management

For a simple single-VM deployment, a supervisor is required because each `blocks run` process stays attached to its terminal. The following example assumes a Bash/Linux VM. PM2 is one optional choice:

```bash
npm install -g pm2
pm2 start npm --name spane-expert --cwd "$PWD/spane-expert" -- run run
pm2 start npm --name blocks-streaming-expert --cwd "$PWD/blocks-streaming-expert" -- run run
pm2 start npm --name integrated-knowledge-agent --cwd "$PWD/integrated-knowledge-agent" -- run run
pm2 save
pm2 status
```

`pm2 save` stores the process list; it does not by itself configure reboot recovery. Run the PM2 startup command it prints for the VM's init system, then test a reboot before treating the deployment as production-ready. A systemd service, container supervisor, or three separate terminals are valid alternatives. Keep each agent's `.env` local to that agent directory and restrict its file permissions. Provision production secrets through the VM's secret-management process rather than copying developer credentials.

## 6. Smoke-test the deployment

With the corresponding `blocks run` process active, run each trigger from its own directory. These triggers are **network smoke tests**: they call the registered agent through Blocks; they do not execute the handler purely offline.

```bash
cd spane-expert
npm run trigger

cd ../blocks-streaming-expert
npm run trigger

cd ../integrated-knowledge-agent
npm run trigger
```

A successful test should submit the sample questions, receive an artifact, and print the response. Also open the agent dashboard at [app.blocks.ai](https://app.blocks.ai) and confirm each registered agent is online and receiving tasks.

If a trigger reports that the agent is offline, confirm that the matching agent process is running, the trigger's `agentName` matches `agent-card.json`, and the process has outbound access to Blocks.

## 7. Publish after private verification

Do not publish until all three private agents pass their smoke tests. Publishing changes the registered agent's visibility and billing; it does not move the process to Blocks-hosted infrastructure.

### Public and free

Run from each agent directory:

```bash
blocks publish --billing-mode free --listing public --accept-terms
```

### Public and paid per task

These agents declare `taskKinds: ["request"]`, so per-task pricing is the appropriate paid model:

```bash
blocks publish \
  --billing-mode paid \
  --listing public \
  --price-per-task 0.01 \
  --accept-terms
```

Use the actual price approved for the project. Per-minute pricing is intended for long-lived `pipe` agents and should not be selected for these request-only cards without first changing and revalidating the agent contract.

Important: after an agent is public or paid, use `blocks publish` for future visibility/pricing updates. Running `blocks register` again resets it to private and free.

## 8. Updates and rollback

For a routine update, first record the currently working CLI/SDK versions and keep the previous dependency state available for rollback. The repository currently uses `latest` and has no lockfiles, so production deployments should pin tested versions and commit lockfiles before relying on automated updates. Replace `X.Y.Z` below with the exact version validated in staging:

```bash
blocks upgrade
npm install --save-exact @blocks-network/sdk@X.Y.Z
npm install
npm run check
npm install --package-lock-only
```

Commit the resulting `package-lock.json` and record the CLI version from `blocks version`. Do not commit a literal placeholder or use an unpinned `latest` dependency for production.

Run the trigger against a private/staging registration before replacing a production process. Then restart the affected `blocks run` process. If the agent is already public or paid, republish with its existing visibility and pricing flags rather than using `blocks register`.

Recommended release sequence:

1. Stop or drain the affected process.
2. Deploy the new code and CSV data.
3. Run `npm install` and `npm run check`.
4. Start `blocks run` and run the trigger.
5. Confirm online presence and successful artifacts in the dashboard.
6. Roll back the code/data and restart if the smoke test fails.

Never commit `.env` or expose `BLOCKS_API_KEY` in logs, CI output, issue reports, or screenshots. Rotate the key if it is exposed.

## 9. Deployment checklist

- [ ] Node.js 22+ and the Blocks CLI are installed.
- [ ] Each project has a working generated `.npmrc` and a protected `.env`.
- [ ] `.env` and `node_modules/` are ignored by Git, verified with `git check-ignore`.
- [ ] Production dependency versions are pinned and lockfiles are retained for rollback.
- [ ] `npm install` succeeds in all three directories.
- [ ] The JSON input contract is verified by `blocks check` and a private trigger.
- [ ] `npm run check` succeeds in all three directories.
- [ ] All three agents are registered privately and free.
- [ ] All three `blocks run` processes stay online.
- [ ] All three `npm run trigger` smoke tests return artifacts.
- [ ] Dashboard presence and task activity are confirmed.
- [ ] Public listing, billing mode, and pricing are intentionally selected before `blocks publish`.
- [ ] A restart and rollback procedure is documented for the chosen VM.
